# GUI evolution — information hierarchy (P31)

**Джерело для фази 31.** ROADMAP: [ROADMAP.md](ROADMAP.md) § NEXT.

Інтерфейс уже функціонально насичений, тому потрібна не перебудова, а упорядкування інформаційної ієрархії. Поточні обмеження розміру вікна варто залишити, оскільки наявна геометрія візуально оптимальна.

## Пріоритетні поліпшення

| Пріоритет | Поліпшення | Результат |
|-----------|------------|-----------|
| 1 | Уніфікувати рядок хоста | Стан мережі читається за секунду |
| 2 | Додати компактну панель деталей вибраного хоста | Менше діалогів і перемикань |
| 3 | Чітко розділити стан endpoint і маршруту | Усунення неоднозначності |
| 4 | Ввести єдину систему severity | Узгоджені кольори, іконки та повідомлення |
| 5 | Поліпшити роботу з великою кількістю хостів | Швидша навігація без ускладнення GUI |
| 6 | Централізувати фонові операції | Зрозумілий стан застосунку |
| 7 | Скоротити й упорядкувати налаштування | Менша когнітивна складність |
| 8 | Поліпшити доступність | Інтерфейс не залежить лише від кольору |

## 1. Уніфікований рядок хоста

Кожен рядок повинен мати стабільну структуру:

```text
[стан] Назва / адреса       RTT   Loss   Mode   [проблема]
```

Правила:

- головний індикатор — доступність endpoint;
- RTT і loss вирівняні за колонками;
- режим позначений коротко: PING, TRACE, MTR;
- route change не конкурує кольором з endpoint failure;
- додаткові дані відкриваються tooltip або деталями;
- висота рядків однакова незалежно від довжини тексту.

Не варто виводити ASN, rDNS, timestamps і пояснення безпосередньо в рядок — він стане нестабільним і перевантаженим.

## 2. Панель деталей вибраного хоста

У Extended mode доцільно мати компактний inspector поруч із графом або під ним:

- адреса та resolved IP;
- поточний режим;
- last poll;
- RTT, jitter, loss;
- статус endpoint;
- час останньої зміни маршруту;
- активна проблема;
- короткі дії: copy, acknowledge, diagnostics.

Панель має оновлюватися при виборі хоста. Це зменшить кількість окремих modal dialogs.

## 3. Розділення двох незалежних станів

| Стан | Значення |
|------|----------|
| Endpoint | UP, DEGRADED, DOWN, UNKNOWN |
| Route | STABLE, CHANGED, INCOMPLETE, NOT TRACED |

Наприклад, PING_ONLY може показувати Endpoint: UP, Route: NOT TRACED. Відсутність route-даних не повинна виглядати як помилка.

## 4. Єдина система severity

Critical — endpoint недоступний; Warning — стійка деградація RTT/loss; Notice — маршрут змінився; Info — конфігураційна або службова подія; Muted — monitoring вимкнений або даних ще немає.

Severity має однаково визначати: колір; іконку; порядок сортування; badge; запис у timeline; alert. Червоний слід залишити виключно для реальної аварії.

## 5. Робота зі списком хостів

- текстовий фільтр за назвою, адресою і тегом;
- сортування: порядок конфігурації, severity, RTT, loss, last change;
- опція «Проблемні спочатку»;
- лічильники у заголовку: `10 hosts · 1 down · 2 degraded`;
- збереження вибраного сортування та фільтра;
- контекстне меню хоста замість додаткових постійних кнопок.

## 6. Централізований статус фонових операцій

`Monitoring: active · 8/10 enabled · Last cycle: 2 s ago` + тимчасові операції (profile, DB, export, MTU, self-check, telemetry flush). Довгі — progress+cancel; короткі — текст без popup.

## 7–10. Backlog (поза лінійною чергою P31-001…007)

- **Налаштування:** 5 груп (Monitoring, Alerts, Persistence, Telemetry, Appearance); Advanced для рідких полів.
- **Граф:** легенда, target hop, timeout marker, Fit, tooltips — без анімації маршруту.
- **Помилки:** що / чому / чи продовжується моніторинг; без modal для тимчасових probe errors.
- **Доступність:** див. §10 оригіналу (іконки UP/DEGRADED/DOWN, contrast, focus, a11y names).

## Оптимальний обсяг лінійної черги (фаза 31)

1. **P31-001** — уніфікований host row  
2. **P31-002** — Endpoint/Route states  
3. **P31-003** — inspector вибраного хоста

5. **P31-005** — фільтр, сортування, «Проблемні спочатку»
